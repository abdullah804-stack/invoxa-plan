store submission and the pilot all need accounts, secrets or explicit authorization from the owner
of the project. This file lists what is ready, what to do, and exactly what is missing.

## 1. Database (MongoDB Atlas, free)

1. Create a free M0 cluster (512 MB, shared).
2. Create a database user with a strong password, scoped to the `invoxa` database.
3. Network Access: allow `0.0.0.0/0`. Render's free service has no static outbound IP, so a
   narrower allow-list is not possible on the free plan.
4. Copy the `mongodb+srv://…/invoxa?retryWrites=true&w=majority` string. This is `MONGODB_URI`.

The free cluster pauses after 30 days without connections. Opening the app counts as a connection.

## 2. API (Render, free)

1. Push the repository (already on `main`).
2. Render → **New → Blueprint** → connect the repository. Render reads `render.yaml` and asks for
   the values marked `sync: false`:
   - `MONGODB_URI` — the Atlas string above.
   - `CORS_ORIGINS` — the Netlify URL from step 3, https only. Until the web site exists, set the
     eventual URL or leave it empty and add it later (an empty value blocks every cross-origin
     browser call, which is safe).
   - `GEMINI_API_KEY` — optional.
3. Apply. Render builds with `npm ci && npm run build:shared && npm run build --workspace
@invoxa/api`, starts `node dist/server.js`, and checks `GET /api/v1/health`.
4. Confirm the first deploy: `curl https://<api-host>/api/v1/health` returns
   `{"status":"ok","service":"invoxa-api"}`.
5. Add repository secrets for the daily job (Settings → Secrets and variables → Actions):
   `API_URL` (the Render URL, with or without `/api/v1`) and `JOB_SECRET` (the value Render
   generated). Until both exist, the workflow skips with a warning.
6. Free plan behaviour: the service sleeps after 15 idle minutes and takes about a minute to wake.
   The app already shows "The server is taking a while to wake up" and retries a backup part.

## 3. Web build (Netlify, free)

1. Netlify → **Add new site → Import an existing project** → pick the repository. `netlify.toml`
   supplies the build command (`npm run build:web`), the publish directory (`apps/mobile/dist`), the
   single-page redirect and asset caching.
2. Site settings → Environment variables → add `EXPO_PUBLIC_API_URL`, e.g.
   `https://<api-host>/api/v1`. It is baked into the bundle, so changing it needs a redeploy.
3. Deploy, then copy the site URL.
4. Set `CORS_ORIGINS` on Render to that URL (comma separated for more than one) and let the API
   restart.
5. Check in a browser: the site loads, signing in works, and a wrong-origin request is refused.

Verify the build locally first:

```bash
npm run build:web     # writes apps/mobile/dist (git-ignored)
```

## 4. Android release (EAS + Play Console)

```bash
cd apps/mobile
npx eas-cli login
npx eas-cli build --platform android --profile preview     # APK for the pilot
npx eas-cli build --platform android --profile production   # AAB for the store
```

- `app.json` already has `version: 1.0.0`, `android.versionCode: 1`, `ios.buildNumber: "1"` and the
  package `app.invoxa.mobile`. Bump both version fields before every store upload; the EAS config
  uses the local values (`appVersionSource: local`).
- The first `eas build` creates the project on Expo and asks to generate a keystore. Keep that
  keystore: losing it means a new package identity.
- Install the preview APK on a real phone and run `docs/phone-checklist.md` before submitting.
- Play Console: create the app, fill the listing from `docs/store-listing.md`, upload the AAB to
  the internal testing track, answer the data-safety form, add the privacy-policy URL and the
  account-deletion URL.
- iOS needs the same steps with an Apple Developer account; nothing in this repository has been
  built for iOS.

## 5. Monitoring and keep-warm

- Host health: Render's health check path is `/api/v1/health`; a failing check marks the deploy
  unhealthy.
- Errors: Render's log stream shows Fastify's request and error logs, with secrets redacted. Every
  response carries `x-request-id` (also exposed through CORS), so a user's report can be matched
  to the exact log line.
- Uptime: point a free monitor (UptimeRobot or similar) at `/api/v1/health`. It alerts when the
  service is down and doubles as a keep-warm ping.
- **Keep-warm trade-off:** a GitHub Actions cron every 10 minutes would be 4,320 runs a month and
  GitHub bills at least one minute per run, which is more than the ~2,000 included minutes. An
  external monitor every 5–10 minutes keeps the service awake but uses ~720 of the 750 free
  Render instance-hours, leaving no headroom. The app's waking message is the free default; add a
  ping only if that trade-off is acceptable.

## 7. Backup and rollback

- Atlas' free cluster has **no automated backups**. Before the pilot, export each business through
  **Settings → Data & privacy → Backup** and keep the JSON files off the database host. The export
  is complete and restorable in parts, so it is the recovery path.
- API rollback: Render → the service → **Deploys** → pick the last good deploy → **Rollback**.
- Web rollback: Netlify → **Deploys** → publish a previous deploy.
- Mobile rollback: an installed app cannot be rolled back, so keep API changes additive during the
  pilot and avoid removing fields or endpoints.

## 8. Pilot with five owners

1. Recruit five small-business owners who invoice real clients.
2. Give each the preview APK (or the web URL) and one 30–45 minute session: sign up, brand the
   business, create and send one real invoice, record a payment.
3. Do not help unless they are blocked; note every hesitation, wrong tap and question.
4. Record each finding with the owner, date, what they tried, what happened and how severe it is.
5. Write the post-launch list only from those notes, ordered by how many owners hit it. Known
   candidates from the plan are online payment links and server-sent email, but they go on the list
   only if the pilot actually asks for them.

## 9. Release gate

The release is done when all of these are true:

- [ ] The API is live with the production variables and `GET /api/v1/health` returns 200.
- [ ] The web build is live and can sign in and invoice against the API.
- [ ] The Android build is installed from the store or an internal track.
- [ ] `docs/phone-checklist.md` is complete on a real phone, including the large-text and
      slow-phone checks.
- [ ] CI is green on `main`.
- [ ] A stranger installs the app and sends a real invoice without help.
